# Element Guidelines

These guidelines cover how to design, build, and publish an Element that users can copy into their projects.

## Design

### Use real videos as references

If you use AI to build an Element, it often designs it like a website component, sized and styled for a page rather than a video. Published videos make a better reference. In a video, text and graphics usually need to be larger so viewers can read them at a glance, and simpler designs tend to work better.

### Keep it focused

Users add Elements to their own projects and combine them into a larger video. This works best when each Element does one thing. An Element that bundles several things, such as a title with its own background, is harder to fit in.

Aim for one visual treatment, technique, or workflow per Element, ideally one that works without configuration and fits many projects. A preset, a small CSS change, or a different set of Studio control values usually doesn't need its own Element.

### Animate temporary Elements in and out

If an Element appears over other content for a short time, such as a lower third, give it an entrance and an exit animation. Backgrounds don't need them.

Animate the parts inside the Element, not its position on screen. Studio sets the position, so the user can move the Element and the animation moves with it.

## Build

### Make it portable

- Keep the implementation self-contained, using HTML, CSS, and React where possible.
- Avoid global styles, layout side effects, and fullscreen assumptions unless the Element is a background.
- Set explicit defaults for inherited visual properties, so the Element looks the same under light and dark host themes:
  - Set text colors on the Element root or the nearest visual surface instead of relying on browser or host-page defaults.
  - Make sure every use of `currentColor` resolves from an ancestor with an explicit color.
- Avoid project-specific branding or footage, and make colors easy to change.

### Dependencies

Minimize dependencies.

Declare every external dependency in the Element library's metadata, except `react`, `react-dom`, and `remotion`. Every non-Remotion package must use an exact semantic version; version ranges and tags are not accepted. Remotion packages use `version: null` and are installed at the project's Remotion version. See the [Studio protocol's `dependencies` field](/docs/studio-protocol/create-element-payload#dependencies).

### Assets

Include assets that should be copied into the user's project. Use Google Fonts for non-websafe fonts.

Follow the [asset integration guidance](/docs/studio-protocol/component-library-integration#preview-installed-assets). Installed assets are separate from gallery previews. Declare installed assets in the library metadata and use [`staticFileRef()`](/docs/studio-protocol/static-file-ref) references in `installationProps`. Keep preview URLs in `initialProps`.

## Integrate with Studio

### Choose an installation mode

Where possible, expose the Element's layers so users can edit them with [Studio interactivity](/docs/studio/interactivity). Pick an installation mode based on what users should see in Studio.

#### Separate editable layers

`installationMode: 'wrapped'` is the default. Studio wraps the component in a [`<Sequence>`](/docs/sequence) that sets its placement and duration, and the layers inside stay editable through their `Interactive` call sites.

Size the Element to its smallest useful bounding box. If it adapts to the composition, set both dimensions to `null`.

#### One interactive object

Use `installationMode: 'component-owned-sequence'` when editing the internal parts doesn't make sense, for example for generative effects, canvas drawings, or a single image overlay.

Wrap the exported component in [`Interactive.create()`](/docs/interactive-create) and export it directly, without another wrapper. The component must accept a `style` prop and apply it to its visual root. Check in Studio that it shows up as one layer that users can move and trim.

Don't use this mode just to hide markup, and don't add padding just for the gallery preview.

### Expose useful controls

Users get a copy of the Element's source and can edit it directly, so the `Interactive` schema doesn't need to expose every detail. Add controls with [`Interactive.create()`](/docs/interactive-create) where they make the Element easier to edit. Controls can tune the look, but shouldn't switch between unrelated styles.

Give editable objects clear names. Use a generic name such as `Container` for the main object, and add child controls only for parts users edit separately. See the [interactivity best practices](/docs/studio/interactivity-best-practices).

### Initial props

If the Element needs starter props, provide [`initialProps`](/docs/studio-protocol/create-element-payload#initialprops) in its library metadata. For `component-owned-sequence`, this can provide defaults for Inspector controls. Otherwise, users can edit the installed source directly.

`installationProps` shallowly overrides `initialProps` only for installation; an overridden object or array replaces that entire prop.

## Publish

### Choose a representative preview

Choose a poster frame that clearly shows the Element. The video preview should cover the Element's full duration and, when applicable, include its entrance and exit animations.

To submit an Element to the official gallery, read the [contribution guide](/elements/contributing).
