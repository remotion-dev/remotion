Encoding is the process of converting a sequence of images into a video file.  
Besides rendering frames, encoding is one of the two steps required to create a video.

From Remotion v4.0.228, Remotion supports hardware-accelerated encoding in some cases.  
Since encoding is platform- and codec-specific, only a few scenarios are supported at the moment.

- macOS: Acceleration using VideoToolbox
- Linux and Windows: Acceleration using NVENC (requires an NVIDIA GPU) (from v4.0.484)
- Linux: Acceleration using VA-API (AMD and Intel GPUs) when `REMOTION_VAAPI_DEVICE` is set (from v4.0.546)
- ProRes is supported from v4.0.228, H.264 and H.265 are supported from v4.0.236

## Enable hardware accelerated encoding

By default, hardware acceleration is `"disable"`.  
You can set the `hardwareAcceleration` option to `"if-possible"` to enable hardware acceleration if it is available.  
If you want the render to fail if hardware acceleration is not possible, set the option to `"required"`.

### In SSR APIs

Use the [`hardwareAcceleration`](/docs/options/hardware-acceleration) option in the [`renderMedia()`](/docs/renderer/render-media) function.

```tsx twoslash {8}
const serveUrl = '/path/to/bundle';
const outputLocation = '/path/to/frames';

import {renderMedia, selectComposition} from '@remotion/renderer';

const inputProps = {
  titleText: 'Hello World',
};

const composition = await selectComposition({
  serveUrl,
  id: 'my-video',
  inputProps,
});

// ---cut---

await renderMedia({
  composition,
  serveUrl,
  codec: 'prores',
  outputLocation,
  inputProps,
  hardwareAcceleration: 'if-possible',
});
```

### In the CLI

Use the [`--hardware-acceleration`](/docs/options/hardware-acceleration) option in the `npx remotion render` command.

```bash
npx remotion render MyComp --codec prores --hardware-acceleration if-possible
```

### In the Studio

In the [Remotion Studio](/docs/studio), you can set the hardware acceleration option in the "Advanced" tab when rendering a video.

### With the config file

You can set the [`setHardwareAcceleration()`](/docs/config#sethardwareacceleration) option in the [config file](/docs/config).

```ts twoslash
import {Config} from '@remotion/cli/config';

Config.setHardwareAcceleration('if-possible');
```

### In Remotion Lambda and Cloud Run

These options are not supported in Remotion Lambda and Cloud Run, because those cloud services do not support hardware acceleration.

## Prerequisites for NVENC (Linux/Windows)

To use hardware-accelerated encoding on Linux and Windows, you need:

- An NVIDIA GPU (GeForce, Quadro, or Tesla)
- NVIDIA drivers installed (version 525+ recommended)
- FFmpeg compiled with `h264_nvenc` or `hevc_nvenc` encoder support

The FFmpeg binaries bundled with Remotion include the `h264_nvenc` and `hevc_nvenc` encoders on Linux x64 and Windows x64. The bundled Linux ARM64 binaries do not include NVENC support.

The presence of these encoders in FFmpeg does not guarantee hardware acceleration. A compatible NVIDIA GPU and driver are still required.

Set `--hardware-acceleration if-possible` and Remotion will use NVENC if the configured FFmpeg build supports it.

Note that NVENC encoding is only available for H.264 and H.265 codecs. Other codecs fall back to software encoding, with these exceptions when hardware acceleration is `"required"`: `h264-mkv` and `h264-ts` throw an error on every platform, and ProRes throws an error on Linux and Windows.

## Prerequisites for VA-API (Linux, AMD and Intel)

To encode on an AMD or Intel GPU on Linux, you need:

- A VA-API render node, for example `/dev/dri/renderD128` (in Docker: `--device /dev/dri`)
- A VA-API driver for the GPU (Mesa's `radeonsi` for AMD, `iHD` for recent Intel GPUs)
- FFmpeg compiled with VA-API: the `h264_vaapi` or `hevc_vaapi` encoder and the `hwupload` filter

The FFmpeg binaries bundled with Remotion do not include VA-API. [`binariesDirectory`](/docs/renderer/render-media#binariesdirectory) replaces all of Remotion's binaries at once (`ffmpeg`, `ffprobe`, Remotion's compositor and their shared libraries), so prepare a complete folder:

1. Copy the folder of your platform's compositor package, for example `node_modules/@remotion/compositor-linux-x64-gnu`.
2. Replace `ffmpeg` and `ffprobe` in it with a build that has VA-API (`--enable-vaapi`: the `h264_vaapi` and `hevc_vaapi` encoders and the `hwupload` filter) and `libfdk_aac`, which Remotion uses for AAC audio.
3. Pass that folder to the render.

```bash
REMOTION_VAAPI_DEVICE=/dev/dri/renderD128 npx remotion render --hardware-acceleration if-possible --binaries-directory ./vaapi-binaries
```

Without `--binaries-directory`, the bundled FFmpeg is used: it has no VA-API, so `"if-possible"` falls back to software encoding.

With the variable set, H.264 is encoded with `h264_vaapi` and H.265 with `hevc_vaapi`; without it, Linux uses NVENC as before. Before the render, Remotion encodes one frame with the selected encoder on the device. If that fails (no VA-API in the FFmpeg, a device the process cannot open, a GPU without an encoder for the codec), `"if-possible"` falls back to software encoding and `"required"` throws an error.

VA-API is only selected for what it encodes exactly: the `yuv420p` pixel format (the frames are uploaded as NV12, so other pixel formats such as `yuv420p10le` stay on the software encoder) and a [`crf`](/docs/options/crf) of 1 or more. Unlike NVENC, VA-API accepts the CRF: it is passed as the constant quantizer (`-rc_mode CQP -qp <crf>`). CRF 0 stays on the software encoder, because FFmpeg treats `-qp 0` as unset.

Some VA-API drivers (Mesa's `radeonsi`) code a 1920x1080 HEVC stream at 1920x1088 without writing the crop. After an `hevc_vaapi` encode, Remotion reads the stream's size and writes the crop with a stream copy when it is larger than the composition. H.265 in MP4 or MOV is tagged `hvc1`, the tag QuickTime and Safari read.

Measured on an AMD Radeon RX 7900 XTX and an RX 6800 XT (Mesa 25.0.7, FFmpeg 8.1): a 568-frame 1080p composition was encoded in under 2 s of GPU time with `hevc_vaapi` against about 127 s of CPU time with `libx264` (`faster`). At `-qp 18` (7900 XTX) and `-qp 16` (6800 XT) the SSIM against a near-lossless reference matched `libx264` at CRF 16 (0.986 against 0.986) at a similar file size.

## Quality using `--video-bitrate` {#controlling-quality-using---video-bitrate}

Note that the file size is significantly larger by default when using hardware acceleration, likely because less compression is applied.  
We recommend that you use the `--video-bitrate` flag to control the file size.

We find that `--video-bitrate=8M` achieves a similar file size than software encoding when exporting a H.264 Full HD video.

The [`crf`](/docs/options/crf), `encodingMaxRate` and `encodingBufferSize` options are not compatible with hardware-accelerated encoders (VA-API takes the `crf` as its quantizer, see above). If you set one of them, a render with `"required"` throws an error, and a render with `"if-possible"` falls back to software encoding. Instead, use the [`--video-bitrate`](/docs/options/video-bitrate) flag to control the quality and file size of the output video.

## Tell if hardware acceleration is being used

[Run the render with verbose logging.](/docs/troubleshooting/debug-failed-render)
If the render is using hardware acceleration, you will see a log message like this:

```
Encoder: prores_videotoolbox, hardware accelerated: true
Encoder: h264_nvenc, hardware accelerated: true
Encoder: hevc_vaapi, hardware accelerated: true
```

Don't rely on the exact wording of the log message to determine if hardware acceleration is being used.
